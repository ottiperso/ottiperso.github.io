Project Overview

In the 2026 ME 218C project, teams designed and built a remote controlled watercraft able to navigate Stanford's Terman Fountain. Each team built two systems: a Quackraft (the watercraft) and a Mallard Module (the handheld wireless controller).

In 6 minute rounds, the objective was to collect toy fauna floating in the fountain, protect Captain Duck figurines from falling off the boat, and dethrone opposing teams' Captain Ducks.

Boat Fuel:

Quackrafts ran on a finite amount of fuel: 40 seconds total, drained by propulsion and use of mechanisms. When fuel was empty, the boat stays still until the Mallard Module operator performed a refueling action (accelerometer detected shaking) for at least 5 seconds.

System Architecture:

Two PIC32MX170F256B microcontrollers (one on the boat, one in the controller) communicated wirelessly via XBee radio modules in API mode at 9600 baud, 5 Hz. All firmware was written in C using the ME218 event driven services framework.

Technical Implementation

Mechanical & Hardware

Quackraft Hull: Catamaran Design:

  • Two parallel foam pontoons bridged by a clear acrylic deck plate
  • Each pontoon has a longitudinal tunnel through which a brushless motor and propeller is mounted
  • Two stacked foam bumpers wrap the deck perimeter per spec (2"–7.5" above waterline)
  • DuckPlate pedestal-mounted at stern, 8" above waterline, edge tangent to interior bumper
  • Max circumference: 6 ft (as per spec)

Fauna Collection System:

  • Open channel between pontoons acts as passive holding bay: fauna float in the interior space under the deck
  • Servo actuated net gate: raised flush for intake, lowered to keep fauna in when reversing
  • Fixed stern net prevents fauna from drifting out the back (without adding drag)

Mallard Module (Controller):

  • Handheld enclosure holding PIC32, XBee module, accelerometer, and all user I/O
  • Analog inputs: two single axis joysticks (left/right motor independent control), potentiometer (boat address selector, teams 1–5), accelerometer (refueling shake detection)
  • Digital inputs: pair button, refuel push button switch, gate switch (SPDT, open/close)
  • Outputs: RGB LED (pairing/drive/refuel status indication), fuel level servo gauge (5 position display)

Electrical

Quackraft Electronics:

  • PIC32MX170F256B for all logic and motor control
  • Two brushless motors with ESCs driven by OC1/OC2 PWM at 50 Hz
  • Gate servo and pairing indicator servo on OC3/OC4
  • XBee on UART2, RX interrupts
  • Power: 7.2V NiMH battery for motors, PDB for logic (3.3V) and servos (5V)
  • All electronics sealed in raised tupperware

Mallard Module Electronics:

  • PIC32MX170F256B for controller logic
  • ADC configured for 4-channel auto scan: accelerometer, knob, L & R joysticks
  • Fuel servo on OC2, RGB LED digital outputs
  • XBee on UART2, RX interrupts
  • Power: 5V USB battery, PDB for logic (3.3V) and servo (5V)

Software Architecture

Event-Driven Framework: Two Independent PIC32 Systems:

Mallard Module Services:

  • ControllerSM: top-level FSM (Idle, Pairing, Driving, Refueling). Manages operator state, fuel servo display, LED output, and posts TX start/stop events to CommSM
  • CommSM: XBee TX/RX service. Sends 13-byte API frames at 5 Hz, parses 10-byte responses byte-by-byte, controls watchdog timer for lost connection
  • LEDService: RGB LED status driver. Blink rate scales with fuel level and blink count shows team number during pairing
  • EventCheckers: polls all physical inputs: pair button, refuel button, mode switch, gate switch, accelerometer threshold, knob zone changes (all with hysteresis)

Quackraft Services:

  • BoatControlSM: boat FSM (Pairing, Driving). Tracks fuel level (drains on movement + stops motors when empty), sets gate servo position, pair/unpair transitions
  • QRCommSM: XBee RX/TX service. Parses incoming API RX packets, validates checksum, checks source address, handles pairing handshake, sends 10-byte responses, manages 4-second unpair watchdog
  • MotorService: ESC PWM driver. Maps 0–255 joystick byte to PWM ticks

XBee Communications Protocol (class-wide standard):

MM → Boat (13 bytes):

  • Delimiter 0x7E, length 0x0009, API ID 0x01
  • Destination address (team-specific, 0x2081–0x2086)
  • Status: 0x00 Drive / 0x01 Charge / 0x02 Pair
  • Joy1 (left motor, 0x00–0xFF), Joy2 (right motor)
  • Digi: bit 0 = gate, bit 1 = duck smacker
  • Checksum: 0xFF − (sum of bytes 4 through n)
  • *When pairing: Joy1/Joy2 repurposed for MM source address

Boat → MM (10 bytes):

  • API RX frame (0x81), source address, RSSI byte
  • Charge byte: 0–150 (fuel level) or 0xFF (pair ACK)
  • *When pairing: 0xFF in charge byte signals successful pairing
  • 4-second silence triggers unpair on boat side
  • Checksum: 0xFF − (sum of bytes 4 through n)
